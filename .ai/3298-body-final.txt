## Why

Poppim issue u2giants/poppim-web#9 proposes a human-confirmed Jev pilot that classifies newly posted product comments as routine updates, blockers/dependencies, decisions, or follow-up reminders. The browser must never hold the provider credential, Jev must never create business records automatically, and ordinary non-admin staff must work through least-privilege database contracts.

The current direct inserts are not a safe foundation: `app.comment.created_by_profile_id` has no default, and the generic `app.comment`, `app.activity`, and `app.notification` write policies are administrator-only. The pilot also needs atomic idempotency, rate limiting, review outcome recording, and exactly-once acceptance without broadening table grants.

## Requested structural contract

1. Add `pim.ai_activity_triage` for redacted provider/result metadata only. It must never store comment text, product title, email, URL, customer/licensor name, credential, or other raw prompt data.
2. Add a unique idempotency key covering comment, normalized-input hash, exact model, and contract version; bounded indexes for caller/review lookups; checks for states and closed labels.
3. Add narrow RLS so a signed-in PM user can read only triage rows they requested and administrators can audit. Direct browser insert/update/delete remains denied.
4. Add `api.pm_add_product_comment(...)` to require an active profile, PM app access, role `administrator` for pilot v1, and caller-readable product; deny viewer/vendor/anonymous; trim and require 1–4,000 characters; allow tab/newline but reject NUL and other control characters; insert with `created_by_profile_id` and return the row. Body edits increment a monotonic `app.comment.body_revision` via a trigger ordinary callers cannot bypass; every triage/eligibility row binds the captured revision.
5. Add `api.pm_begin_activity_triage(...)` to repeat those independent checks, require caller-authored comment on the same product, atomically return an existing result or create/lease one attempt, and enforce a per-profile rolling request limit without a read-then-insert race. The lease has a random token and expiry; fresh leases cannot be stolen. A body edit marks unreviewed non-final triage rows `source_changed` and blocks fence/display/accept.
6. Add signed `api.pm_complete_activity_triage(...)` and `api.pm_fail_activity_triage(...)` wrappers callable under the original caller JWT. They derive the actor from `auth.uid()`, require that actor to remain the row requester, verify an HMAC-SHA-256 canonical envelope using an environment-specific secret read only by the definer from Supabase Vault, and close only the matching current lease. The private implementation is owned by a dedicated NOLOGIN role with rights only on the triage table/functions; authenticated callers cannot execute it directly. Permit stale takeover after at least two provider timeouts; reject late completion from the old lease. This requires no service-role key or custom token issuer.
7. Add `api.pm_get_activity_triage(...)` so the owning user can recover an unreviewed result after tab/product changes or reload. Plan-required recovery surface also includes `api.pm_list_active_jev_triage`, `api.pm_list_reviewed_jev_triage`, `api.pm_record_jev_suggestion_impression`, and requester-only idempotent `api.pm_repair_comment_triage_queue`.
8. Add Jev-independent `api.pm_create_dependency(...)`, `api.pm_create_decision(...)`, `api.pm_create_reminder(...)`, `api.pm_update_dependency_status(...)`, and `api.pm_update_reminder_status(...)`. They enforce the same active-profile/PM-access/staff-role/readable-product checks and exact field allowlists below. Existing manual Operations UI will use these RPCs whether Jev is on or off, so rollback never depends on a triage row.
9. Add `api.pm_accept_activity_triage(...)` and `api.pm_dismiss_activity_triage(...)`. Re-authorize active profile, PM access, allowed staff role, caller-readable product/business unit, and stored actionable label independently of comment ownership. The client cannot choose department or action kind. Field contract: dependency title 1–200 with fixed `blocked_by/open` and no related product; decision type 1–100 and notes ≤2,000 with fixed `decided`; reminder title 1–200, valid optional due date, current caller, fixed `open/follow_up`. Acceptance must lock the triage row, invoke the same validated creation path as the non-AI RPCs, create exactly one record, and mark the outcome in the same transaction. Retry after an ambiguous response returns the original record.
10. Revoke function execution from public/anonymous roles and grant only the exact authenticated wrappers required. Revoke direct execution on private worker functions. Preserve existing table policies; do not add broad table writes or a LOGIN role.

Plan-required reservation/recovery/repair for comment operations: `api.pm_reserve_product_comment_operation`, `api.pm_cancel_product_comment_reservation`, `api.pm_recover_product_comment_handle`, `api.pm_repair_comment_triage_queue`. HMAC envelope verification on begin/complete/fail/fence includes `api.pm_verify_jev_runtime_fence`. Eligibility ledger is `pim.ai_activity_triage_eligibility` (append-only-during-pilot; no raw text).

The app-owned Edge Function source and deployment stay in `poppim-web`; this issue owns only shared database shape and preview/prod migration evidence.
